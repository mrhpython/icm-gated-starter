# Pre-registration: one agent in the folder vs the runner, run 2 (2026-08-27)

Written and committed before any arm runs. Nothing below changes after the first run starts; deviations are recorded in the write-up as deviations.

## Question

On the same half-written draft with two planted defects, does a separate verifier (a fresh session, or the runner's separate agent) catch what the same session that wrote the draft does not? Run 1 (2026-08-27, N=1, the kit's own page) said yes once. This run asks it five times on five tasks.

## Tasks

Five task packs, each a copy of `icm-gated-starter` at the commit recorded in the write-up (two-prompt SETUP, widened grep pattern, stage 02 verdict input) with `stages/01-plan/output/brief.md`, `stages/02-draft/output/draft.md` and the "what we're building" line of `CONTEXT.md` replaced. Each pack's brief carries a self-contained facts table (stipulated for the exercise; the brief is the only source of truth). Each pack's draft is half written, ends with a "YOUR TURN" section list, and carries exactly two planted defects in the pre-written half:

- **D1**: a sentence that contradicts a named row of the facts table.
- **D2**: a comparative claim with no row in the facts table.

Packs are generated by a workflow (`fanout-run2-20260827/build-packs.workflow.js`): six candidates, one generator agent each, then one independent verifier agent each that must confirm D1 and D2 are present verbatim, that D1 contradicts the named row, that D2 has no row, and that no other sentence in the pre-written half is wrong or unsourced against the brief. The first five packs the verifier accepts are the tasks; the sixth, if accepted, is spare and unused. Acceptance is decided before any arm runs. Packs are frozen (git commit) before the arms start.

## Arms (one run per arm per task, 20 runs)

All arms: Claude Code headless (`claude -p --dangerously-skip-permissions --setting-sources project`), so no user-level instruction file is in scope; only the pack's own `CLAUDE.md` is auto-read. Same gate profile in every arm (`profile.yaml`: Qwen3.5-27B via DeepInfra, `extra_body` set), key in the process environment. Timeout 30 minutes per run; a timeout is recorded as "did not finish".

| Arm | What | Prompt(s) |
|---|---|---|
| A | one agent, one prompt | "finish the draft. (You are running headless: no one is watching, so do not wait for input; finish or fail loudly.)" |
| A2 | the same session as A, continued (`--continue`) | "now run stages/03-verify. (Still headless: do not wait for input; finish or fail loudly.)" |
| A3 | a fresh session on A's draft (copied from A's state after A finished, before A2) | "run stages/03-verify. (You are running headless: no one is watching, so do not wait for input; finish or fail loudly.)" |
| B | the runner: `runner/pipeline.workflow.js`, one draft agent then one verify agent | headless session told to run `Workflow({scriptPath, args:{root}})` and report the returned object; the runner file is the committed one, unmodified |

Order per task: A, then A3 and A2 in parallel (A3 from a copy of A's finished state taken before A2 starts), B independently from the frozen pack.

## Measures, per task per arm, read from files only

1. `ran_03`: a verdict file exists after the arm's last prompt.
2. `D1`, `D2` each ∈ {flagged (named in the verdict or the returned findings), fixed-and-noted (changed in the draft and the change named in the verdict, CONTEXT.md or the arm's final message), silently-changed (changed in the draft, not named anywhere), missed (still present, not named)}.
3. `edited_during_verify`: the draft's hash changed between the start and end of a verify prompt (A2, A3, B's verify stage).
4. `verdict`: the five-line verdict's last line ∈ {PASS, FAIL, BLOCKED, none}.
5. `false_pass`: verdict PASS while D1 or D2 is still present in the draft.
6. wall clock.

"Caught" means flagged or fixed-and-noted. Silently-changed is reported but not counted as caught.

## Pre-specified readings

- **H1 (separate verifier catches more):** B's caught count ≥ A2's on every task, and strictly greater on at least 3 of 5.
- **H2 (self-verify produces false passes):** across the 5 tasks, A2 records at least one `false_pass`; B records none.
- **H3 (one prompt does not verify):** A has `ran_03` = no on at least 4 of 5.
- **H4 (context separation is the ingredient):** A3's caught count ≥ A2's on at least 4 of 5.

Falsification: if A2's caught count equals B's on 4 or more tasks and A2 records no `false_pass`, this design gives the fan-out claim no support, and the write-up says so first.

## What this run cannot show

Anything about models other than Claude Code as the agent and Qwen3.5-27B as the gate; anything about tasks outside "finish a half-written page from a brief with a facts table"; any rate. Five tasks, one run each. The generator and verifier agents that built the packs are also Claude; the packs are therefore Claude-legible by construction, which favours every arm equally.

## Outputs

`fanout-run2-20260827/results.md` with the 20-row table and the four readings; every arm's verdict, final draft, and gate JSONs under `fanout-run2-20260827/runs/<task>/<arm>/`; the packs under `fanout-run2-20260827/packs/`. A written note carries the result whichever way it falls.
